# Create GitHub App token with AWS KMS

A JavaScript GitHub Action that creates a GitHub App installation access token without storing a PEM private key in GitHub. It signs the GitHub App JWT with an asymmetric AWS KMS signing key, then exchanges the JWT for an installation token through the GitHub REST API.

The action uses the AWS SDK default credential provider chain. In GitHub Actions, configure those temporary credentials with GitHub OIDC before invoking this action.

## Usage

Store the App ID or Client ID, KMS key ARN, and role ARN as GitHub Actions variables. They are identifiers, not private keys. By default, the action resolves the GitHub App installation for the repository running the workflow. Pin all third-party actions to immutable commits in production.

```yaml
name: Use GitHub App token from KMS

on:
  workflow_dispatch:

permissions:
  contents: read
  id-token: write

jobs:
  example:
    runs-on: ubuntu-24.04
    steps:
      - name: Configure temporary AWS credentials through OIDC
        uses: aws-actions/configure-aws-credentials@e3dd6a429d7300a6a4c196c26e071d42e0343502
        with:
          role-to-assume: ${{ vars.AWS_GITHUB_APP_ROLE_ARN }}
          aws-region: ap-southeast-1

      - id: app-token
        uses: debank/create-github-app-token-kms@v1
        with:
          app-id: ${{ vars.GITHUB_APP_CLIENT_ID }}
          kms-key-id: ${{ vars.GITHUB_APP_KMS_KEY_ARN }}
          aws-region: ap-southeast-1
          permissions: '{"contents":"read"}'
          repositories: '["private-repository"]'

      - name: Use the installation token
        env:
          GH_TOKEN: ${{ steps.app-token.outputs.token }}
        run: gh api repos/debank/private-repository
```

When the workflow operates on the current repository, omit both `installation-id` and `repository`. To create a token for another repository, pass `repository: owner/repository`; to select a specific installation explicitly, pass `installation-id`. At least one of `installation-id`, `repository`, or `GITHUB_REPOSITORY` must be available.

The action masks both the transient App JWT and the installation token. Do not print the output token in workflow logs.

## Inputs

| Input | Required | Description |
| --- | --- | --- |
| `app-id` | Yes | GitHub App client ID (recommended) or app ID used as the JWT `iss` claim. |
| `installation-id` | No | GitHub App installation ID. If omitted, the action resolves the installation for `repository` or `GITHUB_REPOSITORY`. |
| `repository` | No | `OWNER/REPOSITORY` used to resolve an installation when `installation-id` is omitted. Defaults to `GITHUB_REPOSITORY`. |
| `kms-key-id` | Yes | KMS key ARN, alias ARN, alias name, or key ID. |
| `aws-region` | Yes | Region containing the KMS key. |
| `github-api-url` | No | GitHub REST API base URL; defaults to `GITHUB_API_URL` or `https://api.github.com`. Supports GitHub Enterprise Server API URLs such as `https://github.example/api/v3`. |
| `permissions` | No | JSON object that narrows installation-token permissions, such as `{"contents":"read"}`. |
| `repositories` | No | JSON array of repository names that narrows the installation token, such as `["repo-a","repo-b"]`. |

## Outputs

| Output | Description |
| --- | --- |
| `token` | GitHub App installation access token. |
| `expires-at` | ISO 8601 expiration time returned by GitHub. |

## AWS and GitHub configuration

### KMS key

The KMS key must be an asymmetric RSA signing key with:

- `KeyUsage`: `SIGN_VERIFY`
- A key specification compatible with `RSASSA_PKCS1_V1_5_SHA_256`, for example `RSA_2048`
- A private key corresponding to the GitHub App public key

The final condition is essential: creating an unrelated KMS RSA key is not sufficient because GitHub cannot verify JWTs signed by it. If your GitHub App PEM was generated by GitHub, use the same RSA private key as imported asymmetric KMS key material, or use an equivalent key-registration process that ensures GitHub has the corresponding public key. Protect the source key material and understand the operational implications of imported key material before migration.

### IAM permissions

The role assumed by the workflow needs only `kms:Sign` for this KMS key:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "SignGitHubAppJwt",
      "Effect": "Allow",
      "Action": "kms:Sign",
      "Resource": "arn:aws:kms:ap-southeast-1:123456789012:key/KEY_ID"
    }
  ]
}
```

The KMS key policy must also authorize the role (or delegate permission management to IAM in the account). Do not grant `kms:CreateKey`, `kms:PutKeyPolicy`, or broad KMS permissions to the workflow role.

### GitHub OIDC trust policy

Create an IAM OIDC provider for `https://token.actions.githubusercontent.com` with audience `sts.amazonaws.com`. Restrict the role trust policy to the repository and branch or environment allowed to create tokens. For example, for a branch-based subject:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:YOUR_ORG/YOUR_REPOSITORY:ref:refs/heads/main"
        }
      }
    }
  ]
}
```

GitHub repositories using immutable OIDC subject claims or GitHub Environments can have a different `sub` format. Match the actual `sub` claim for the intended workflow identity; do not broaden the policy to arbitrary repositories or refs.

## Development

```bash
npm ci
npm test
npm run build
```

Commit `dist/index.js` with releases. GitHub Actions runs the bundled file directly and does not run `npm install` for consumers.

## Security notes

- The GitHub App JWT exists only in memory and is never an output.
- Installation tokens are sensitive even though they are short-lived. This action masks its output, but downstream workflow steps must not print it.
- Pin this action to an immutable release commit in production; maintain `v1` as a moving major-version tag for convenience only.
- Keep the OIDC trust policy and KMS key policy scoped to the narrowest practical repository, ref, environment, and KMS key.
